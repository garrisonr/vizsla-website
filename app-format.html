How Vizsla apps ship

One app, one file: why we chose AppImage

Every application in Vizsla OS ships as a single AppImage file — one file you can hold, copy, check, keep, or delete. Linux has other ways to package software, and some of them are good. This page explains the choice honestly: what AppImage gives us, what the alternatives genuinely do better, and what AppImage costs us — said out loud, the way we try to say everything here.

The short answer

An AppImage is a whole application packed into one file. There is no installer in the usual sense: you place the file on the machine, and the app runs. Remove it by deleting the file. Go back to the version before by keeping that file and running it instead. Nothing else on the system is touched — no shared parts are swapped under other programs, and no part of the app is scattered across the disk where only a package manager can find it.

Vizsla publishes its applications through its own catalog, in numbered generations. Every file in a generation carries a published fingerprint — a SHA-256 checksum — and the file that lands on every machine is checked against it, byte for byte. The app on one Vizsla machine is not probably the same as the app on another. It is provably the same file.

Why this shape fits Vizsla

One file is the whole app

Install means put the file here. Uninstall means delete it. Rollback means run the previous file — and Vizsla keeps the outgoing version when a new generation lands, so going back is a fact, not a hope. If you can manage a folder of photographs, you already understand how Vizsla software is installed.

Why it matters: a program you can point at is a program you can reason about. Nothing hides in a database, a cache, or a transaction log.

No root, no daemon, no gatekeeper

An AppImage runs entirely in your own user space. It needs no administrator password to install, no background service supervising it, and no app store’s permission to exist. Vizsla apps travel from the people who build them to the people who run them through Vizsla’s own catalog — nobody in between can approve, delay, or quietly remove them.

Why it matters: software that needs a gatekeeper’s blessing can be un-blessed. Ours can’t.

The same file on every base

The machines Vizsla is built and tested on do not all run the same underlying Linux base, and the base has changed before — it will change again; that is planned, not feared. Because an AppImage carries what it needs with it, the identical file runs across those bases. A new base does not mean rebuilding, re-testing, and re-shipping every application.

Why it matters: an operating system that intends to outlive its foundations cannot weld every app to one of them.

Yours to keep, offline and forever

Download a Vizsla app once and it is yours in the plain sense: the file works with the internet unplugged, it cannot be revoked or delisted by a vendor, and nobody can reach into your machine and change it overnight. Keep a shelf of older versions and they will still run years from now.

Why it matters: this is the same promise Vizsla makes about your files, applied to the programs themselves.

Versions on purpose

A catalog generation is the version story. New generations are published deliberately, with names and fingerprints, and a machine moves to one when its owner says so — never because a store decided tonight was the night. There are no silent forced updates in Vizsla, because the format has no mechanism to force one.

Why it matters: an update you didn’t choose, arriving mid-week, changing the tool you rely on, is a landlord’s habit. We are not building a landlord.

The other formats, fairly

None of the alternatives is foolish, and two of them are genuinely excellent at what they aim at. If we only listed their faults, you should not trust the list. Here is each one at its best, and then the specific reason it is not Vizsla’s official format.

Flatpak — the strongest alternative

Flatpak is good technology, honestly built: real sandboxing, shared runtimes so apps stay lean, and a large public catalog. For third-party software you do not know, its sandbox is a genuine protection, and we say so without a smirk. It is not our official format for two reasons. First, the sandbox is also a wall: Vizsla’s own programs do deep system work — a fingerprint reader at the lock screen, GPS hardware, the panel and the lock screen themselves, shared machinery between apps — and a format designed to keep apps away from the system fights the programs whose job is the system. Second, distribution runs through a store and its runtimes and review. Vizsla publishes through its own catalog, on its own generations, and a format that routes around that would route around the promise.

.deb — the native package

The Debian package is the old, proven way: fast, native, integrated with the system by a package manager with decades of mileage. On a single stable system, it is entirely respectable. It fails Vizsla on geography and on manners. A .deb is built for one distribution and one release of it; Vizsla runs across bases, and the same artifact must ship everywhere. Installing one runs scripts as the administrator and can pull, upgrade, or remove other parts of the system to satisfy its needs — one app’s install becomes a negotiation with everything else you own. And when a package transaction goes wrong, what it leaves behind is not a file you can delete; it is a system to repair.

Snap — the vendor’s format

Snap has real engineering in it: transactional updates and confinement are features, not marketing. But a Snap cannot exist without its background service, its store is run by one company as the only store there is, and that store’s server side is not open — the format has a landlord built into its foundations. Updates refresh on the store’s schedule whether or not the moment suits you, and the format has long been criticized for slow first starts. Vizsla’s founding argument is that nobody should stand between a person and their own computer. Snap stands there by design.

What AppImage costs us — said out loud

A page that only praised its own choice would be an advertisement. AppImage has real weaknesses, and we accept them with our eyes open:

  • The files are bigger. Each app carries its own libraries instead of sharing the system’s, so a shelf of apps weighs more than the same shelf installed the native way. Disk space is the price of one-file independence; we pay it knowingly.
  • No shared-library patching. When a system library is fixed, native packages heal everywhere at once. An AppImage carries its own copy, so the fix only reaches it when the app is rebuilt. Our answer is the catalog itself: when a library is fixed, the affected apps are rebuilt and republished as a new generation — the discipline is ours to keep, and it is a discipline, not a mechanism.
  • No update channel of its own. An AppImage will never nag you, because it cannot update itself at all. Vizsla’s catalog generations are the channel: visible, numbered, and taken when the owner chooses.
  • No sandbox by default. AppImage does not wall an app off from your files the way Flatpak does. Vizsla’s own applications are first-party programs, written for this system and published with their fingerprints in the open — we choose trust you can verify over a wall our own system programs would spend their lives climbing. For software from strangers, that trade deserves a second thought, and this page will not pretend otherwise.

The pattern underneath all four: AppImage moves work from machinery to us. Nothing is automatic, supervised, or enforced by the format itself — the catalog, the fingerprints, and the generations are habits Vizsla keeps on purpose. We would rather keep a promise ourselves than rent one from a format.

What this means for you

Most days, nothing — and that is rather the point. Your apps are files, in a place you can find, that you can copy to a stick, lend to a neighbour’s machine, archive against a rainy decade, or delete without ceremony. The roster of what ships this way is on What’s inside, and how Vizsla itself arrives on a machine is on Install & Ferry. If a program of ours ever stops deserving its place on your disk, the removal instructions are one sentence long: delete the file. It was always yours.
